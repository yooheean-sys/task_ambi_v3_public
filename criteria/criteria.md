# 裁定基準表 v1 — 4層カンバン組織の判断点分類

- 最終更新: 2026-10-15（役割名の同期: doc_lead→public_relation・実行9役→実行12役（presenter・communication 追加）。保守系第三層 maintenance_procedures と実行3役（vault / harness / kaizen）を追加し実行12役→実行15役。基準本体は v1.1 から変更なし）
- 適用者: 分解・検収専任の5役（planner / project_lead / system_engineer / public_relation / maintenance_procedures）
- 実行15役はこの表を直接適用しない。子タスク本文に書かれたラベルに従い、ラベル外の判断点に直面したときは §4 の経路に従う
- 「誰に聞くか」の判断は上位3層の専権。**実行ワーカーは人間に直接質問しない**

## 1. 3つのラベル

| ラベル | 定義 | 判断者 |
|---|---|---|
| 【裁定：人間】 | 不可逆な操作。価値・要件の解釈。基準外の判断 | 人間 |
| 【裁定：上位層】 | 可逆かつ技術的な判断。ただし複数の案があり成果物の形が変わるもの | 分解・検収専任の5役 |
| 【裁量：実行ワーカー】 | 既定の型に沿う実装の詳細。上位層の検収で逸脱なら差し戻せる | 担当の実行ワーカー |

## 2. 判定手順（fail-safe 付き）

この順で問う。どこにも当てはまらなければ**【裁定：人間】**とする（基準外＝人間）。

1. 不可逆か（元に戻せない、または戻すのに特別な手間・外部影響を伴う）? → はい =【裁定：人間】
2. 価値・要件の判断か（データでは決まらず、人間の方針・好みでしか決まらない）? → はい =【裁定：人間】
3. 成果物の形が変わる技術選択か（アーキテクチャ・ライブラリ・データ構造・方針）? → はい =【裁定：上位層】
4. 型に沿う実装詳細か? → はい =【裁量：実行ワーカー】
5. どれにも当てはまらない（基準外）? →【裁定：人間】

マトリクスで整理:

| | 技術的判断 | 価値・要件判断 |
|---|---|---|
| **可逆** | 【裁定：上位層】／【裁量：実行ワーカー】 | 【裁定：上位層】 |
| **不可逆** | 【裁定：人間】 | 【裁定：人間】 |

具体例:

- 【裁定：人間】: 本番デプロイの実施・削除・外部サービスへの登録・受入条件の変更・成果物の公開可否・費用が発生する選択・期限の変更・この表に載らない判断
- 【裁定：上位層】: テストフレームワークの選定・データ構造や API 形状の決定・ディレクトリ構成・文書の章立ての方針・依存ライブラリの選定
- 【裁量：実行ワーカー】: 関数や変数の命名・関数の分割の粒度・見出しの文言・コメントの書き方・テストケースの細部

## 3. 通信経路のルール

### 分解時（上位3層が判断点を持ったとき）

- 【裁定：人間】は、**子タスクを起票する前に**自カードで人間に問う。実データに基づく候補と推奨・理由を添えて kanban_block（kind='needs_input'）を呼び、回答を kanban_show で読んでから結論を子タスク本文に明文化して完了する。**実行フェーズに人間の回答待ちを残さない**
- 【裁定：上位層】はその時点で結論を出し、kanban_comment に候補・根拠・選択理由を記録して子タスク本文に反映する

### 実行中（実行ワーカーがラベル外の判断点に直面したとき）

1. **人間に直接質問しない**（needs_input を自分で呼ばない、質問を kanban 以外の媒体で送らない）
2. 【裁定依頼】タイトルのカードを親役（自カードの親カードの assignee）に起票する。本文に: 判断点の内容・実データ・候補（候補ごとの該当件数や根拠）・推奨と理由
3. 自カードを依頼カードの子として kanban_link し、kanban_block（kind='dependency'）で待つ
4. 依頼カードが完了すると自動で再開する。裁定は依頼カードの comment スレッドで読む（再 spawn 時に全文読まれる）

### 【裁定依頼】カードの処理（上位3層）

- 基準表に従って分類し、【裁定：上位層】相当なら自ら結論を出し、kanban_comment に候補・根拠・選択理由を記録して完了する
- 【裁定：人間】相当（基準外を含む）なら候補と推奨を添えて自カードを needs_input にし、人間の回答を kanban_comment に転記して完了する
- 依頼元の実行カードは kanban_unblock で動かさない（依頼カードの完了が依存を解き、自動再開させる）

## 4. 記録義務

- 上位層が裁定した点は、必ず kanban_comment に候補・根拠・選択理由を残す（ブラックボックス化の防止・検収の根拠）
- 実行ワーカーの【裁量】判断は、完了申告の summary に含める

## 5. 検収不合格の処置（2026-10-05 v1.1 追加。sample5_rework の検証結果に基づく）

- 検収役が kanban_request_changes で差し戻すとき、理由には**未充足点**に加えて**波及同期対象**を明記する。修正が成果物の挙動・出力・I/F を変える場合（確定通知による仕様変更を含む）、その仕様に依存する成果物（テスト／テスト報告書／機能報告書／マニュアル等）を検収役が列挙する
- 同期は**「テスト → 報告書」の順**で行う（報告書は検収済みのテスト結果を根拠にするため）。テスト・報告書が旧仕様のまま残ると、成果物セット全体が「一貫性のない検収済み」状態になる（sample5 で実測: 実装修正後に tests 3 failures・test_report「全件合格」が虚偽化）
- 同期は修正カードの**完了後**に、検収役が同期カードを起票する（テスト同期 → 報告書同期の依存チェーン）。人間検収由来の修正カード（人間が起票する場合）も同じ構成にする
- 修正カードの受け入れ条件には「依存成果物を変更していない」を必ず入れる（修正スコープの封じ込め）。波及の回収は同期カードの責務とし、修正カードに混ぜない
