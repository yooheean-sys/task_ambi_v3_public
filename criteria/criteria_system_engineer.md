# 裁定基準（役別）— system_engineer

## 0. 適用と読み込み順序

- 本表は共通コア `criteria.md`（v1.1）に対する **system_engineer 固有の上書き・追加条項**のみを定める。本表に書かれていない点は共通コアに従う
- 共通コアを先に読み、その上に本表を適用する。**競合時は本表を優先**する。ただし本表は共通コアを緩める方向に書かない（緩める改訂が必要な場合は共通コア側の改訂として人間に提案する）
- 適用対象は system_engineer の分解・検収の全行為。配下の実行役（architect / programmer / debugger / test_engineer / devops / code_reviewer / specification_writer）は共通コアの実行役規定に従い、本表を直接適用しない

## 1. 判断点分類の追加・具体化

共通コア §2 の判定手順はそのまま使う。以下はプログラム・調査系統の判断点の具体化:

| 判断点 | 分類 | 補足 |
|---|---|---|
| devops タスクの `.env*`・鍵ファイル・クレデンシャルを扱う操作 | 【裁定：人間】 | 共通コア「不可逆」の具体化。起票本文に禁止条項を明記し、直面したときは共通コア §3 の経路で人間裁定に回す |
| devops タスクの `rm -rf`・`git push --force`・本番への不可逆操作 | 【裁定：人間】 | 同上。実行側は実行せず kanban_comment と成果物に記録して人間へ |
| 依存ライブラリの追加・バージョン固定 | 【裁定：上位層】 | 依存構成が成果物の形を変える選択。候補と根拠を comment に記録してから子本文に反映 |
| テストフレームワーク・CI 構成の選定 | 【裁定：上位層】 | 共通コアの具体例どおり |
| debugger の修正方針（根本原因のどこを直すか） | 【裁定：上位層】 | 挙動・I/F を変える修正は、起票前に波及同期対象（テスト・報告書）を共通コア §5 に従って列挙する |
| 関数の分割粒度・変数命名・テストケースの細部 | 【裁量：実行ワーカー】 | 共通コアの具体例どおり |

- 調査系タスクの成果物形式（報告書の形式・必須記載項目・参照リンクの付け方）は、起票時に system_engineer 自身が確定して子の本文に書く。形式を書かないまま子へ委ねない（形式が検収条件に影響するため）
- 本表に無い判断点は共通コアの fail-safe（基準外＝【裁定：人間】）に従う

## 2. 検収の役別確認事項（共通コア §5 への追加）

レビュアーとして呼ばれたとき、共通コアの検収プロセスに加えて:

- **実体検証を必須とする**: 成果物プログラムの再実行・テスト実行・出力の検算のうち少なくともひとつを実際に実行し、その出力を根拠に合格判定する。summary・artifacts の申告だけでは合格を出さない
- 波及同期対象の列挙は、修正が挙動・出力・I/F を変える場合に**テスト → 報告書の順**の同期チェーンを必ず含める
- 検収・再検証に使った一時フィクスチャ・確認用データは workspace 内に残す。/tmp 等に置くと後から突合できない

## 3. 改訂

- 本表の改訂候補は kanban_comment に「改訂候補: criteria_system_engineer.md …」で始まる1文を記録し、人間が本ファイルを改訂する
- 共通コア側の改訂候補は、共通コア §6 のとおり criteria.md 宛に記録する
