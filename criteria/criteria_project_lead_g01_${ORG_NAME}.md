# 裁定基準（役別）— project_lead_g01_${ORG_NAME}

## 0. 適用と読み込み順序

- 本表は共通コア `criteria.md`（v1.1）に対する **project_lead_g01_${ORG_NAME} 固有の上書き・追加条項**のみを定める。本表に書かれていない点は共通コアに従う
- 共通コアを先に読み、その上に本表を適用する。**競合時は本表を優先**する。ただし本表は共通コアを緩める方向に書かない（緩める改訂が必要な場合は共通コア側の改訂として人間に提案する）
- 適用対象は本役の分解・検収の全行為。配下に起票した子タスク（第3層3役）とその配下の実行役は、共通コアの実行役規定とそれぞれの SOUL に従い、本表を直接適用しない
- 本表は **g01_${ORG_NAME} 専用**である。他プロジェクトのタスクが割り当てられた場合は誤配として needs_input で人間に渡し、本表を適用して判断しない

## 1. 判断点分類の追加・具体化（project_lead 共通）

共通コア §2 の判定手順はそのまま使う。以下は分解設計の判断点の具体化:

| 判断点 | 分類 | 補足 |
|---|---|---|
| 分解設計: 子の数・第3層3役（system_engineer / public_relation / maintenance_procedures）への振り分け・並列/直列の依存構成 | 【裁定：上位層】 | 本役が結論を出し、候補と根拠を kanban_comment に記録してから子を起票する |
| 子タスクの workspace 選定（既存実在ディレクトリのどこにするか） | 【裁定：上位層】 | workspace_kind='dir' ＋ workspace_path=<接頭辞なし絶対パス>。契約（.hermes.md）に基づき決定 |
| 成果物先として契約外の新規ディレクトリを作る選択 | 【裁定：人間】 | 起票本文でユーザー承認を得てから作成する。自判断で作らない |
| 契約（.hermes.md）の記載と `ls` 実測のズレの検出 | 【裁定：人間】 | 実測を優先して子タスク・本表は実在名で書き、食い違いを kanban_comment に記録する。契約側の修正は人間が行う |
| 標準構成で未配備のディレクトリ（minutes / public_relations / schedule 等）の作成 | 【裁定：人間】 | 無いプロジェクトで勝手に作らない。必要なら needs_input（xxx_others_pj は §2 が優先） |
| 受け入れ条件の成果物ファイル名の割り当て | 判断点にならない（絶対規則） | 親の受け入れ条件から原文のまま引き継ぐ（言い換え禁止） |
| 子の本文に書く参照パスの推測 | 判断点にならない（絶対禁止） | 不明なら `ls` で実在確認するか needs_input。実在しないパスを書かない |
| 子の本文の節構成・文言の細部 | 【裁量：実行ワーカー】 | 型に沿う詳細。本役自身の細部判断を含む。上位層（planner）の検収で逸脱なら差し戻される |

- 子の本文への必須伝播事項（§2 に列挙）は判断点ではなく**必須の伝播義務**。起票本文から省略しない
- 本表に無い判断点は共通コアの fail-safe（基準外＝【裁定：人間】）に従う

## 2. プロジェクト固有の上書き・追加条項

- 本節はディレクトリ契約の要約ではなく**裁定の追加**である。契約の正本はプロジェクトルートの `.hermes.md` であり、本節と契約・実測が食い違うときは契約（実測優先）に従い、食い違いを人間に報告する
- **拠点**: プロジェクトルート `${ORG_ROOT}`（ext4 の Python モノレポ git リポジトリ・9p ではない）。vault 系標準ディレクトリ構成の**対象外** — 既存のリポジトリ構成が契約
- **第二拠点（2026-10-17 人間承認で追加）**: ${REPO_NAME} リポジトリ `${REPO_ROOT}`（origin `${GITLAB_URL_ORG}/${REPO_NAME}.0.git`。GitLab グループ ${ORG_NAME} は本プロジェクトと同じ）。調査・読み取り・GitLab issue コメント投稿を主とする。リポジトリ配下へのファイル追加・変更は原則禁止（必要な場合は【裁定：人間】）。python は uv 前提・`.env` を触らない・固有内容を memory / skill_manage に保存しない の各条項を準用する
- **権限の3区分は契約どおり**: 編集可 = `services/` `tests/` `specs/`（SDD: `specs/<番号>-<名前>/` の実在構成に従う）`docs/` `plans/` `ci/` `Makefile` `docker-compose*.yml` `pyproject.toml`／読み取りのみ = `.specify/` `signoz/` `test-artifacts/` `logs/` `speckit_memory_backup/` `.env.example`／触らない = `.env` `.git/` `.venv/` `__pycache__/` `.kilo/` `.roo/` `.clinerules`。**区分の追加・変更は【裁定：人間】**
- **成果物先**: `plans/`・`docs/`・`specs/`（`outcomes/` は存在しない。勝手に作らない）
- **必須伝播事項（子の本文に必ず含める）**: ①python は uv 前提（`uv add` / `uv run`。`pip install` 禁止）②テストは `make test`（無ければ `uv run pytest`）③`.env` を触らない条項 ④子には対象 service（`services/<名>`）と対応する `specs/` の契約テスト確認を明示 ⑤固有内容を memory / skill_manage に保存しない
- 9p の in-place 上書き条項は不要（ext4）

## 3. 検収の役別確認事項（共通コア §5 への追加）

レビュアーとして呼ばれたとき、共通コアの検収プロセスに加えて:

- **実体検証を必須とする**: 成果物プログラムの再実行・テスト実行・出力の検算のうち少なくともひとつを実際に実行し、その出力を根拠に合格判定する。summary・artifacts の申告だけでは合格を出さない
- 契約整合: 成果物先が `.hermes.md` 契約・受け入れ条件どおりのパス/ファイル名であることを確認する（原文引き継ぎの検証）
- 伝播検証: §2 の必須伝播事項が子の本文に書かれていたかを確認する。伝播漏れによる下位の逸脱は分解側の問題として扱う
- workspace 確認: 各子の Events の workspace_kind/workspace_path が契約どおりであることを確認する
- 成果物が `plans/`・`docs/`・`specs/` のいずれかに置かれ、`outcomes/` が勝手に作られていないことを確認する
- テスト成果物は `make test`（または `uv run pytest`）を実際に実行して判定する
