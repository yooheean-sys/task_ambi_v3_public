# 裁定基準（役別）— public_relation

## 0. 適用と読み込み順序

- 本表は共通コア `criteria.md`（v1.1）に対する **public_relation 固有の上書き・追加条項**のみを定める。本表に書かれていない点は共通コアに従う
- 共通コアを先に読み、その上に本表を適用する。**競合時は本表を優先**する。ただし本表は共通コアを緩める方向に書かない（緩める改訂が必要な場合は共通コア側の改訂として人間に提案する）
- 適用対象は public_relation の分解・検収の全行為。配下の実行役（content_writer / structure_designer / analyst / presenter / communication）は共通コアの実行役規定に従い、本表を直接適用しない

## 1. 判断点分類の追加・具体化

共通コア §2 の判定手順はそのまま使う。以下は文書・広報系統の判断点の具体化:

| 判断点 | 分類 | 補足 |
|---|---|---|
| 文書・資料の公開・送信・投稿の実行 | 【裁定：人間】 | 共通コア「成果物の公開可否」の文書系具体化。communication は文案作成のみで送信・投稿しない |
| 文書の宛先・読み手・目的の変更 | 【裁定：人間】 | 価値・要件判断。起票本文の契約で確定させておくべき点 |
| 文書の章立て・構成の方針 | 【裁定：上位層】 | structure_designer への委任判断。候補と根拠を comment に記録してから子本文に反映 |
| プレゼン資料（Marp/pptx 等）のスライド構成 | 【裁定：上位層】 | 章立てと同型。枚数・装飾などの細部は【裁量】 |
| analyst の分析軸・指標の選定 | 【裁定：上位層】 | 分析結果の形が変わる選択 |
| 見出し・段落の文言、文体・表記の細部 | 【裁量：実行ワーカー】 | 共通コアの具体例どおり |

- 文書系の成果物先（どのディレクトリのどのファイル名で出すか）は、親カードの受け入れ条件から**原文のまま**引き継ぐ。ファイル名の言い換えは検収不合格の原因になる
- 本表に無い判断点は共通コアの fail-safe（基準外＝【裁定：人間】）に従う

## 2. 検収の役別確認事項（共通コア §5 への追加）

レビュアーとして呼ばれたとき、共通コアの検収プロセスに加えて:

- 成果物の存在確認に加えて**実際に読んで**以下を確認する: 成果物先ディレクトリ・ファイル名が契約どおり／受け入れ条件の各項目に対応する内容が存在する
- communication・presenter の成果物は「送信・投稿の実行を含まない」ことを確認する。実行まで含む成果物は不合格
- 章立て方針（structure_designer 判断）が後から変わった場合、既存の下流文書（報告書・要約等）との整合を確認する。旧構成のまま残る文書があれば共通コア §5 の波及同期対象として列挙する

## 3. 改訂

- 本表の改訂候補は kanban_comment に「改訂候補: criteria_public_relation.md …」で始まる1文を記録し、人間が本ファイルを改訂する
- 共通コア側の改訂候補は、共通コア §6 のとおり criteria.md 宛に記録する
